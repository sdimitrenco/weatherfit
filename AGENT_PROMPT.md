# AGENT_PROMPT — Telegram Weather Bot (Go + Open-Meteo)

## 1. Роль и цель

Ты — senior Go-разработчик. Задача: спроектировать и реализовать **личного Telegram-бота**, который каждый день в **07:00 (Europe/Berlin)** присылает мне прогноз погоды на день: почасовой список, ветер с оценкой силы, осадки, вердикт «нужна ли защита от дождя» и совет, как одеться.

Бот для одного пользователя (меня). Приоритеты: надёжность утренней рассылки > читаемость сообщения на телефоне > простота кода > фичи.

## 2. Правила работы (обязательны)

1. **Сначала вопросы, потом код.** Прежде чем писать код, задай мне одним сообщением все развилки из раздела 9 — по каждой дай 2–3 варианта, свою рекомендацию и почему. Жди моего ответа.
2. **Никаких молчаливых архитектурных решений.** Если по ходу работы появляется новая развилка (библиотека, формат хранения, изменение структуры) — остановись, опиши варианты, жди решения. Мелкие решения внутри слоя принимай сам и упоминай в отчёте.
3. **Проверяй факты по живым источникам.** Перед реализацией клиента открой актуальную документацию https://open-meteo.com/en/docs и сверь имена переменных. Сделай один реальный запрос и сохрани ответ как fixture для тестов. Версии Go-библиотек проверяй по их репозиториям, не по памяти.
4. **Работаем майлстоунами** (раздел 10). После каждого: тесты зелёные, коммит в формате Conventional Commits, короткий отчёт — что сделано, что проверено, что осталось.
5. Не выдумывай данные. Если чего-то нет в ответе API — показывай «—», а не подставляй значение.

## 3. Контекст и конфигурация

- Локация по умолчанию: **Дрезден**, `lat=51.05`, `lon=13.74`, `TZ=Europe/Berlin`. Всё настраивается через env.
- Язык сообщений бота: **русский**.
- Режим получения апдейтов: **long polling** (не webhook) — боту не нужны входящие порты и домен.

Переменные окружения (`.env.example` обязателен):

```
TELEGRAM_BOT_TOKEN=
TELEGRAM_ALLOWED_CHAT_IDS=123456789        # через запятую
LOCATION_NAME=Дрезден
LOCATION_LAT=51.05
LOCATION_LON=13.74
TZ_NAME=Europe/Berlin
REPORT_TIME=07:00
ACTIVE_HOURS=07-22                          # часы, которые показываем и по которым считаем советы
WIND_UNIT=ms                                # ms | kmh
LOG_LEVEL=info
```

Конфиг валидируется при старте; при ошибке — понятное сообщение и exit 1.

## 4. Функциональные требования

### 4.1 Утренняя рассылка
- Ежедневно в `REPORT_TIME` по `TZ_NAME` (переходы на летнее/зимнее время должны работать корректно).
- Отправка всем chat_id из whitelist.
- Если Open-Meteo недоступен: ретраи с экспоненциальным backoff (например 5 попыток в течение ~15 минут). Если так и не вышло — отправить короткое сообщение «Не удалось получить прогноз, попробуй /today позже» и залогировать ошибку.

### 4.2 Команды
- `/start` — приветствие + список команд.
- `/today` — тот же отчёт, что утром, но с текущего часа до конца активного окна.
- `/tomorrow` — отчёт на завтра (все активные часы).
- `/help` — список команд.
- Сообщения от chat_id не из whitelist: ответить «Это приватный бот», залогировать chat_id на уровне info (чтобы я мог добавить себя при первой настройке).

## 5. Данные: Open-Meteo Forecast API

Endpoint: `GET https://api.open-meteo.com/v1/forecast` — без API-ключа, бесплатно для некоммерческого использования.

Параметры запроса:

```
latitude, longitude
timezone=Europe/Berlin
forecast_days=2                 # всегда 2 дня, нужный день фильтруем сами (для /tomorrow)
wind_speed_unit=ms              # или kmh по конфигу
hourly=temperature_2m,apparent_temperature,precipitation_probability,precipitation,
       rain,showers,snowfall,weather_code,wind_speed_10m,wind_direction_10m,
       wind_gusts_10m,uv_index,is_day
daily=temperature_2m_max,temperature_2m_min,apparent_temperature_max,apparent_temperature_min,
      precipitation_sum,precipitation_probability_max,wind_speed_10m_max,wind_gusts_10m_max,
      wind_direction_10m_dominant,uv_index_max,sunrise,sunset
```

Важно:
- При заданном `timezone` время приходит как локальное без смещения (`2026-09-10T07:00`) — парсить через `time.ParseInLocation` с нужной локацией.
- HTTP-клиент с таймаутом (10 s), корректный `User-Agent`.
- DTO Open-Meteo не должны протекать в домен — маппинг в адаптере.
- Данные под лицензией CC BY 4.0 → в конце каждого сообщения строка `Данные: Open-Meteo.com`.

## 6. Бизнес-правила (домен)

Все пороги — именованные константы в domain-слое, покрыты table-driven тестами. Правила детерминированные.

### 6.1 WMO weather_code → иконка и текст

| Код | Иконка | Текст |
|---|---|---|
| 0 | ☀️ (ночью 🌙) | ясно |
| 1 | 🌤 | преимущественно ясно |
| 2 | ⛅ | переменная облачность |
| 3 | ☁️ | пасмурно |
| 45, 48 | 🌫 | туман |
| 51, 53, 55 | 🌦 | морось |
| 56, 57 | 🌧🧊 | ледяная морось |
| 61, 63, 65 | 🌧 | дождь (слабый/умеренный/сильный) |
| 66, 67 | 🌧🧊 | ледяной дождь |
| 71, 73, 75, 77 | ❄️ | снег |
| 80, 81, 82 | 🌦 | ливневый дождь |
| 85, 86 | 🌨 | снегопад |
| 95 | ⛈ | гроза |
| 96, 99 | ⛈ | гроза с градом |

Неизвестный код → ❔ и лог warning.

### 6.2 Ветер

Направление в API — **откуда дует**. Стрелка в сообщении показывает, **куда дует**. Это частый баг — покрыть тестами, включая границы 0/360 и 337.5/22.5.

| Откуда | Румб | Стрелка |
|---|---|---|
| 0° | С | ↓ |
| 45° | СВ | ↙ |
| 90° | В | ← |
| 135° | ЮВ | ↖ |
| 180° | Ю | ↑ |
| 225° | ЮЗ | ↗ |
| 270° | З | → |
| 315° | СЗ | ↘ |

Индекс румба: `int((deg + 22.5) / 45) % 8`.

Сила ветра (средняя скорость, м/с, по мотивам шкалы Бофорта):

| м/с | Уровень | Метка |
|---|---|---|
| < 1.6 | штиль | 🍃 |
| 1.6 – 5.4 | слабый | 🍃 |
| 5.5 – 7.9 | умеренный | 🌬 |
| 8.0 – 13.8 | сильный | 💨 ⚠️ |
| ≥ 13.9 | очень сильный / штормовой | 🌪 ⛔ |

Порывы: если `wind_gusts_10m ≥ 14 м/с` (~50 км/ч) — отдельное предупреждение «порывы до N м/с». Если единица км/ч — пороги пересчитываются, логика та же.

### 6.3 Осадки и вердикт «нужна ли защита от дождя»

Считаем только по **активным часам**.

- **Не нужно** — во всех часах вероятность < 30% или осадки < 0.1 мм.
- **На всякий случай** (зонт в сумку) — есть час с вероятностью 30–59% и осадками ≥ 0.1 мм, либо вероятность ≥ 60%, но осадки < 0.3 мм (морось).
- **Обязательно** — есть час с вероятностью ≥ 60% и осадками ≥ 0.3 мм/ч, либо сумма за активные часы ≥ 2 мм при максимальной вероятности ≥ 50%.
- **Сильный дождь** — есть час ≥ 2.5 мм/ч или сумма ≥ 10 мм → дополнительно «непромокаемая обувь».

Модификаторы:
- «Обязательно» + ветер ≥ 8 м/с или порывы ≥ 14 м/с → советовать **дождевик / куртку с капюшоном вместо зонта** (зонт при таком ветре бесполезен).
- Коды 95–99 → предупреждение о грозе ⛈.
- Коды 56, 57, 66, 67 → предупреждение о гололёде.
- `snowfall > 0` или снежные коды → совет про зимнюю обувь.
- Окна осадков: склеивать соседние «мокрые» часы в интервалы и выводить «дождь 14–17 ч», а не перечислять каждый час.

### 6.4 Совет по одежде

База — **ощущаемая температура** (`apparent_temperature`) в активные часы: минимум определяет, что надеть утром, максимум — можно ли снять верхний слой.

| Ощущается | Базовый комплект |
|---|---|
| ≥ 25° | футболка, шорты/лёгкие брюки, головной убор |
| 18 – 24° | футболка, джинсы/лёгкие брюки |
| 12 – 17° | лонгслив или худи + лёгкая куртка/ветровка |
| 5 – 11° | свитер + демисезонная куртка |
| 0 – 4° | тёплая куртка, шапка |
| −10 – −1° | зимняя куртка, шапка, шарф, перчатки |
| < −10° | пуховик, термобельё, всё тёплое |

Модификаторы:
- Разница max − min ≥ 8° → «одевайся слоями: утром X, днём можно снять Y».
- Ветер «сильный» и выше → ветрозащитный верх / капюшон.
- Вердикт по дождю из 6.3 встраивается в совет.
- UV ≥ 3 → солнцезащитные очки; UV ≥ 6 → ещё SPF и головной убор.

Текст совета собирается из шаблонов: 2–4 коротких предложения, без воды.

## 7. Формат сообщения

- `parse_mode=HTML` (не MarkdownV2 — меньше проблем с экранированием). Весь динамический текст экранировать (`<`, `>`, `&`).
- **Первые строки — вердикт.** В push-уведомлении видны только первые ~100 символов, поэтому главное (зонт/не зонт, как одеться) должно быть в самом начале.
- Строка почасового списка должна помещаться в ширину экрана телефона без переноса (ориентир ~34 символа). Проверь рендер в реальном Telegram (мобильный клиент) на майлстоуне 4.
- Сообщение < 4096 символов (лимит Telegram).

Целевой вид (значения условные):

```
☂️ Бери дождевик — дождь 14–17 ч
🧥 Утром ~12°: худи + лёгкая куртка

🌦 Дрезден · четверг, 10 сентября
🌡 13° → 22° (ощущается 11…21°)
💨 Ветер ЮЗ ↗ до 9 м/с — сильный, порывы 14
☀️ УФ 5 · 🌅 06:35 · 🌇 19:30

⏱ По часам
07 ☁️ 13°   0%        🍃 2 З→
08 ☁️ 14°   0%        🍃 3 З→
…
14 🌧 19°  80% 1.2мм  💨 9 ЮЗ↗ ⚠️
15 🌧 18°  90% 2.0мм  💨 9 ЮЗ↗ ⚠️
…
22 🌙 14°  10%        🍃 3 З→

👕 Как одеться
Утром прохладно — худи и лёгкая куртка, днём до 21°, куртку можно снять. С 14 до 17 дождь и сильный ветер: дождевик с капюшоном вместо зонта. Обувь лучше непромокаемую.

Данные: Open-Meteo.com
```

Если форматирование эмодзи-строками плохо выравнивается — предложи вариант с моноширинной таблицей в `<pre>` и покажи оба, решение за мной.

## 8. Архитектура

Clean Architecture, строгое разделение слоёв: бизнес-логика не знает про Telegram, HTTP и Open-Meteo.

```
cmd/weatherbot/main.go            — сборка зависимостей, graceful shutdown (SIGINT/SIGTERM)
internal/
  config/                         — загрузка и валидация env
  domain/                         — Forecast, HourPoint, DaySummary, WindLevel,
                                    RainVerdict, OutfitAdvice + чистые правила из раздела 6
  usecase/
    build_report.go               — получить прогноз → проанализировать → вернуть Report
    send_morning_report.go        — build + отправка всем получателям + ретраи
  port/                           — интерфейсы: ForecastProvider, Notifier, Clock
  adapter/
    openmeteo/                    — HTTP-клиент, DTO, маппинг в domain
    telegram/                     — бот: команды, whitelist, отправка
    render/                       — Report → Telegram HTML
    scheduler/                    — ежедневный запуск в REPORT_TIME
testdata/                         — fixture-ответы Open-Meteo (реальный + синтетические кейсы)
```

Требования:
- `Clock` как интерфейс — чтобы тестировать «текущий час» и дату без реального времени.
- Логи: `log/slog`, JSON в проде.
- Таймзоны: `import _ "time/tzdata"`, чтобы `time.LoadLocation` работал в минимальном Docker-образе.
- `context.Context` пробрасывается везде, отмена при shutdown.

## 9. Развилки — спросить меня до начала кода

1. **Telegram-библиотека:** `github.com/go-telegram/bot`, `gopkg.in/telebot.v4` или `go-telegram-bot-api/telegram-bot-api/v5`. Сравни по активности поддержки на текущий момент и удобству.
2. **Планировщик:** `robfig/cron/v3` с `cron.WithLocation` или собственный цикл «спать до следующего 07:00».
3. **Единицы ветра по умолчанию:** м/с или км/ч.
4. **Почасовой список:** каждый час в активном окне или шаг 2–3 часа (короче сообщение).
5. **Совет по одежде:** только правила (детерминированно, бесплатно, тестируемо) или правила + опциональная LLM-переформулировка через Claude API за интерфейсом `AdviceGenerator` с fallback на правила.
6. **Хранение состояния:** только env (MVP) или SQLite, если настройки (время, локация) меняются командами бота.
7. **Пропущенная рассылка:** если сервис перезапустился после 07:00 — досылать отчёт при старте (нужно хранить дату последней отправки) или нет.

## 10. План по майлстоунам

1. **Каркас** — структура проекта, `go.mod`, config + валидация, `slog`, Makefile (`run`, `test`, `lint`, `build`, `docker`), `.env.example`, golangci-lint.
2. **Open-Meteo клиент** — запрос, DTO, маппинг, реальный fixture, тесты через `httptest.Server`.
3. **Доменные правила** — ветер (сила, румб, стрелка), осадки и вердикт, окна дождя, одежда. Table-driven тесты на все пороги и границы.
4. **Рендер** — Report → HTML, golden-тесты на несколько сценариев (солнечный день, дождь + сильный ветер, снег, гроза). Отправить тестовое сообщение мне в Telegram и показать, как выглядит.
5. **Telegram-бот** — команды, whitelist, обработка ошибок отправки.
6. **Планировщик** — ежедневный запуск, ретраи, сообщение об ошибке. Тест с фейковым `Clock`.
7. **Docker и деплой** — multi-stage Dockerfile (distroless или alpine), `docker-compose.yml` с `restart: unless-stopped`, `DEPLOY.md` с инструкцией для моего сервера. Входящие порты не открываются.
8. **Полировка** — README со скриншотом-примером, финальная проверка по Definition of Done.
